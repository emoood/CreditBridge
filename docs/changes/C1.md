## 5. API

- `PATCH /api/v1/applications/{id}/header` body `{value?, major?}` (only fields sent change; blank clears). Returns the header view. 409 outside the review gate.
- `POST /api/v1/applications/{id}/reevaluate` body `{scope: field|row|page, row_id?, field?, page?, confirm_overwrite?}`. Returns `{proposals: [{row, field, old, new, same, block, pos, matched, by, at}], notes: [{row?, field?, why}], calls_used, calls_budget}`. 409 for: edited field without `confirm_overwrite` ("Edited by X on D."), a row added by hand, budget used, a case that replays a recording ("needs Live AI"), layout mismatch. 502 if the provider fails (nothing changed).
- `POST /api/v1/applications/{id}/rows/{row}/reeval/{field}` body `{choice: new|old}`. Returns the row. 404 if there is nothing to choose.
- `GET /api/v1/demo/recordings` returns `[{name, variant, case_number, current, reason, name_ok}]`.
- `GET /applications/{id}`: `extraction.header = {value, student_type, major, major_missing, source, major_source, basis, disagrees, curriculum_check, edited}`, `extraction.credits = {show, required, missing}`, rows `credits_missing`, `edited`, `reeval`.
- `POST /applications` with `demo=1`: 409 `Recording out of date: <why>. Re-record it, or switch to Live AI.`

## 6. How it works

1. **Speed.** `layout()` cuts a page at the widest white gap, so A2 is 3 whole-term blocks (was 4 slices). The Intake agent gets the listing in its first message and reads every block with course rows in one `read_block` call; `finish()` has code read what is left and ask about every failing cell.
2. **Header.** The agent reports `institution_curriculum` and `major` in `submit_courses`. `build_header` normalises it, cross-checks the PDF text layer (agent wins, a disagreement is shown, a value only the text layer gave is labelled "text layer (code)") and stores it in `ctx.name_check["header"]`, because `pipeline.py` (not in C1's list) persists `name_check` whole. Student type, credits rules and the case-record comparison are computed when the application is read (`header_view`, `_detail`), so an officer edit takes effect at once.
3. **Re-evaluate.** `reevaluate` finds the row's block (`locate_rows`: the i-th extracted row is the i-th course row of the stored readings), rebuilds the layout, and calls `reread_blocks` (300 dpi, same `read_once`, `MeteredProvider`, ledger via `usage.log_tool`). The prompt names the row position, never a value. `build_proposals` stores differences on the row as `reeval`. Nothing in the table changes. `resolve_reeval` with `new` calls `apply_proposal` (value, mark/points, `edited` with `via: re-read`, answered questions dropped, `recheck_row`), re-links the course if the title changed (an officer's own link is kept), and `recompute_extraction` redoes term and cumulative totals from the stored readings with the chosen values laid over them (stored readings are not modified). Eligibility, mapping and placement run after Confirm from the confirmed rows, as before, so they need no recompute at this stage.
4. **Replay.** `data_version` is a SHA-256 of every file under `policies/data/` (CRLF to LF for text files); `reading_version` is `PROMPT_VERSION + LAYOUT_VERSION`. Upload and `DemoProvider` both check them.
